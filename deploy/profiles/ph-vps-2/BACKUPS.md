# Encrypted backups and restoration

Reporting date: 2026-11-09 (Asia/Shanghai). Evidence files retain their machine-generated UTC timestamps. No production deployment, real player changes, live Cloudflare changes or credential rotation were performed.

backup.sh is an operator-installed template using a separately provisioned **off-host restic repository** and private MariaDB defaults/password files. It refuses local repository schemes, has a bounded background service envelope, streams a consistent InnoDB dump into encrypted storage without writing plaintext SQL on the VPS, uses pipefail and an exclusive backup lock, and marks snapshots pending-restore. A successful upload/integrity sample is not a successful restore. [Restic stdin backup](https://restic.readthedocs.io/en/stable/040_backup.html) and [restoration](https://restic.readthedocs.io/en/stable/050_restore.html) are the reference procedures.

Provision a dedicated least-privilege backup identity, an authenticated remote backend with object immutability where available, and separately escrow recovery credentials. Keep secrets under /etc/maxhigh with restrictive ownership/modes; do not put passwords in arguments, repository files, public metrics or logs. The script's scheme check does not prove that a configured remote is physically off-host: verify the backend and credentials operationally. No remote credentials or transfer were available in this task.

Install the reviewed backup service/timer only with separate approval. The template schedules 03:15 Asia/Manila with up to 15 minutes jitter; confirm the owner's RPO, traffic window and alerting requirements first. Back up and retain the release compatibility policy and approved artifact manifests alongside recovery evidence; review absolute pointer paths when restoring to another host. Full daily snapshots alone can lose up to a day. Ship encrypted binlogs and verify a complete recovery chain if a smaller financial RPO is required. Seven-day local binlog expiry must never outrun verified off-host coverage. No automatic destructive repository forget/prune policy is enabled.

Weekly and after schema/backup changes: select an explicit snapshot ID, restore to a new isolated MariaDB instance/schema using matching supported versions and an account unable to touch live schemas. Verify authentication/integrity before applying SQL. Check row counts and hashes, user balances against signed ledgers, operation IDs/codec readability, paid-feature state, FK/orphan integrity, migration checksums and representative application startup. Run point-in-time recovery drills and measure RTO. Store evidence with the snapshot ID; only then mark the backup verified. Never run a restore command against the live database.

Executed local evidence: an AES-256-GCM encrypted, compressed **disposable fixture** dump restored into a new audit schema; all 21 table row hashes matched and ciphertext tampering failed authentication. This validates local dump/restore/data retention, not restic backend access, external retention, production recovery, Ubuntu 10.11 restoration or the binlog recovery chain. Those gates remain open.
