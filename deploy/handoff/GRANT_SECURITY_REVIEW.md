# Entitlement grant mechanism - security review

Scope: the developer-signed grants that unlock games, lift the client-account cap or authorize an exempt account
(`src/server/access-policy.server.ts`, `src/server/access-admin.server.ts`, `scripts/dev/sign-entitlement-grant.mjs`).
**No signing key exists. No production key was generated. Restrictions are inactive.** This review describes the code as built; limitations are listed in section 9 and are not hidden.

## 1. Algorithm and key handling
* **Ed25519** (RFC 8032) through Node `crypto.sign/verify`. The signature covers the **exact UTF-8 bytes** of the payload string, so any change to any byte, including whitespace, invalidates it.
* **Private key:** held only by the developer, offline. It never exists in the repository, the build, the VPS or the database. `sign-entitlement-grant.mjs` refuses a key file located inside the repository and prints only payload + signature.
* **Public keys:** compiled into the build (`grantKeys: [{id, publicKeyPem}]`). Shipped value: **empty**, therefore *no grant can be accepted by any build that does not list a key* (verified: unit test "unknown key id" and the shipped-policy test).
* **Key id:** every grant names the key that signed it; an unknown id is rejected before any signature work.
* **Custody decision is open** (who holds the key, where its backup is stored). A real key must be generated by that custodian on an offline machine; I did not and will not generate it.

## 2. Validation performed on every grant
1. Size limits (payload <= 8,192 bytes, signature <= 256 characters).
2. Known key id; Ed25519 signature valid over the exact payload.
3. Strict schema (zod discriminated union): `v = 1`; `kind` in {`unlock-games`, `lift-client-cap`, `authorize-exempt-account`}; `nonce` 16-64 chars; `issuedAt` valid datetime; optional `expiresAt`; kind-specific fields (game ids restricted to `[a-z0-9-]{1,64}`, 1-100 ids; cap integer 0-1000; username `[a-z0-9_]{3,64}` and class `qa|admin`). Unknown kinds and malformed ids are rejected.
4. `environment` must equal the environment compiled into the build (`uat`): a UAT grant cannot be applied to another environment.
5. `expiresAt`, when present, must be in the future **at apply time**.
Applying additionally requires: superadmin session, password re-confirmation (with the existing lockout counter), and the typed phrase `APPLY SIGNED GRANT`.

## 3. Scope
Each grant is narrow and explicit: a list of named games, one numeric cap, or one named account with a class. There is no wildcard and no "unlock everything" kind. A grant cannot lock anything or change policy.

## 4. Replay protection
`nonce` is unique in `entitlement_grants`; re-applying returns "This grant was already applied" (tested). The environment binding prevents cross-environment replay. After a database **restore from before** the grant was applied, the same signed grant can be applied again (same effect; no new authority is created).

## 5. Tamper resistance of stored grants
Stored grants are **re-verified on every load** (cache 5 s). A row inserted directly into the database without a valid signature grants nothing (tested end to end). Editing a stored payload or signature breaks verification.

## 6. Revocation
* There is **no signed "revoke" grant**. Behaviour today: removing a row from `entitlement_grants` (database access) re-locks the game; removing a public key id from `grantKeys` in a new release makes every grant signed by that key stop verifying (games re-lock, the cap returns to the policy value).
* `expiresAt` limits the window in which a grant may be **applied**; it is **not re-checked after application** (see limitation 9.1).

## 7. Key rotation and recovery
* **Rotation:** add the new public key to `grantKeys` in a release (keep the old key listed), issue replacement grants signed by the new key, apply them, then remove the old key in a later release. Removing an old key first would silently re-lock games it unlocked.
* **Loss of the signing key:** no new grants can be created. Grants already applied keep working while their public key stays in the build. Recovery path: the developer ships a new reviewed release (new key and, if needed, a policy change). This is why the key backup must be part of the custody decision.
* **Compromise of the signing key:** an attacker also needs a superadmin session, the password and the confirmation phrase to apply anything. Response: release a build that removes the compromised key id (re-locks what it unlocked) and re-issue grants with a new key.

## 8. Audit trail
`entitlement.apply` (kind, key id, nonce, actor), `game.locked_attempt` (action, game, actor), `account.create_rejected` (attempt, layer), `restrictions.activate` (developer script) - all in the append-only audit log; applied grants are also stored verbatim in `entitlement_grants`. Audit insertion is best-effort (a failed audit write is logged, not fatal), so database availability, not the audit table, is the limiting factor.

## 9. Known limitations (honest list)
1. **Expiry is apply-time only.** An applied grant with `expiresAt` stays effective after that date. Fix if wanted: re-check expiry in `loadEffectiveGrants` (one-line change plus test); deliberately not changed here because it would re-lock games unexpectedly at a clock time.
2. **No signed revocation kind**; revocation needs database access or a new release.
3. `issuedAt` is validated as a date but not compared with the clock (a pre-signed future-dated grant is accepted); the signature is the authority.
4. A cap grant can raise the limit but a later lower value has no effect (the highest valid value wins); lowering needs a release.
5. These restrictions are a **commercial control, not tamper-proof DRM**: anyone with root on the server and the ability to redeploy can change the build. They are visible, documented and contract-governed by design.
6. The test-only policy hook (`MAXHIGH_POLICY_TEST_FILE`) exists for end-to-end tests: it is honoured only with `MAXHIGH_POLICY_TEST_OVERRIDE=disposable-test-only` AND a loopback, disposable-named database, and the process **refuses to start** otherwise (unit-tested). It must never be set on UAT or production.

## 10. Behaviour when the signing key is unavailable
Nothing changes at runtime: verification needs only public keys. Existing locks and caps stay as compiled; already-applied grants keep verifying; new grants cannot be produced until the key is recovered or replaced by a release.
